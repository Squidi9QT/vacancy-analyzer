# ADR-006. Сырой SQL вместо ORM

**Статус:** принято

## Контекст
**ORM** (Object-Relational Mapping, например SQLAlchemy ORM или Django ORM) — библиотека, которая представляет таблицы как классы Python и сама генерирует SQL: `session.query(Vacancy).filter(Vacancy.role == 'data_analyst')`.

**Вопрос, который я бы задал:** «Какая цель проекта важнее — скорость разработки или умение писать и читать SQL?»

## Варианты
1. ORM (SQLAlchemy ORM).
2. Построитель запросов (SQLAlchemy Core).
3. Сырой SQL через драйвер psycopg 3 с параметрами.

## Решение
Вариант 3.

## Почему
- Цель проекта — научиться SQL. Системный аналитик на работе пишет SQL руками: в DBeaver, в Metabase, в задачах для разработчиков. ORM спрятал бы именно то, что нужно изучить.
- Аналитические запросы (оконные функции, `percentile_cont`, gaps-and-islands) в ORM пишутся тяжело и читаются хуже, чем SQL.
- `ON CONFLICT ... DO UPDATE` с условиями в ORM требует специфичных для диалекта конструкций — проще написать SQL.
- Запросы лежат в `.sql`-файлах: их можно выполнить в psql и в DBeaver без Python.

## Последствия
- (+) Каждый запрос виден целиком, план можно посмотреть `EXPLAIN`.
- (−) Нет автоматических миграций: схему меняем SQL-файлами `001_`, `002_` вручную.
- (−) Защиту от SQL-инъекций обеспечиваем сами: **только** параметры `%s`, никогда не f-строки с данными (см. «Подводные камни» на сайте).
