# ADR-004. Нормализация навыков

**Статус:** принято

## Контекст
У вакансии список навыков (`key_skills` в API). Работодатели пишут их по-разному: «SQL», «sql», « SQL », «Postgres», «PostgreSQL».

**Вопрос, который я бы задал:** «"Postgres" и "PostgreSQL" — это один навык для отчёта или два?»

## Варианты
1. Строка через запятую в `vacancy.skills`.
2. Массив `TEXT[]` или `JSONB` в `vacancy`.
3. Справочник `skill` + связь `vacancy_skill` (нормализация).

## Решение
Вариант 3. В `skill` два поля: `name` (как выглядел при первой встрече) и `name_normalized` (ключ дедупликации, `UNIQUE`). Нормализация в `src/transform/skills.py`: обрезать пробелы, схлопнуть повторные пробелы, нижний регистр, словарь синонимов («postgres» → «postgresql»).

## Почему
- Строка через запятую не даёт посчитать топ без разбора строки в каждом запросе и не защищает от дублей (см. `docs/data_model.md`, «Почему нормализация»).
- Массив в PostgreSQL рабочий вариант (`unnest`, GIN-индекс), но не переносится на другие СУБД и не даёт хранить свойства навыка (категорию, синонимы).
- Справочник позволяет поменять написание навыка в одном месте.

## Последствия
- (+) Топ навыков — `JOIN` + `GROUP BY`; дубли запрещены первичным ключом `vacancy_skill`.
- (−) Словарь синонимов нужно поддерживать вручную. Новые синонимы в отчёте будут отдельными навыками, пока их не добавят.
- (−) Запись вакансии — несколько запросов (навык, связь), а не один.
