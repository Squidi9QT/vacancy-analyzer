# ADR-005. Стратегия идемпотентной загрузки

**Статус:** принято

## Контекст
Загрузка запускается каждый день, окна запусков пересекаются (`--days 7` ежедневно), загрузка может упасть на середине и её перезапустят. Нужно, чтобы повторная загрузка тех же данных не создавала дублей и не портила историю.

**Вопрос, который я бы задал:** «Что должно произойти, если запустить загрузку дважды подряд? А если она упала на 500-й вакансии из 1000?»

## Варианты
1. **TRUNCATE + полная перезаливка.** Меньше всего кода, но уничтожает историю и `first_seen_at`.
2. **SELECT, потом INSERT или UPDATE в Python.** Между SELECT и INSERT другой процесс может вставить ту же строку (гонка), это два запроса вместо одного.
3. **`INSERT ... ON CONFLICT (hh_id) DO UPDATE`** (upsert) — проверка и запись атомарно в одном запросе.
4. **MERGE** (есть в PostgreSQL 15+) — гибче, но длиннее и менее известен.

## Решение
Вариант 3 для `vacancy`, `employer`, `area`, `skill`, `currency`; `ON CONFLICT DO NOTHING` для `vacancy_skill`. Для истории — сравнение `content_hash` с актуальной версией: новая версия пишется только при изменении.

Дополнительно:
- **Одна вакансия = одна транзакция.** Если упадёт 500-я, первые 499 сохранены, а 500-я откатилась целиком (без «половины» вакансии: строка есть, а навыков нет).
- **`first_seen_at` не перезаписывается** при конфликте: в `DO UPDATE SET` его нет. Поэтому вопрос 5 («новые за 7 дней») работает при любом числе перезапусков.
- **`last_seen_at = GREATEST(старое, новое)`**: повторный запуск за прошлую дату не «состарит» вакансию.
- В пределах одного запуска вакансию, найденную двумя поисковыми запросами, обрабатываем один раз (множество `seen` в `src/pipeline.py`).

## Почему
Атомарный upsert — стандарт для ETL: он не зависит от того, сколько раз и в каком состоянии запускали загрузку.

## Последствия
- (+) Перезапуск после сбоя безопасен — достаточно запустить ещё раз, ничего не чистя руками.
- (+) Тест `test_load_is_idempotent` проверяет: два запуска → одинаковые количества строк.
- (−) Транзакция на каждую вакансию медленнее одной большой (≈1–2 мс накладных расходов). Для тысяч вакансий в день это секунды.
- (−) Удалённые из источника вакансии не удаляются (см. open_questions, вопрос 6).
