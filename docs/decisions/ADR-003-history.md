# ADR-003. Хранение истории изменений

**Статус:** принято

## Контекст
Вакансию после публикации меняют: поднимают в поиске (новая `published_at`), правят зарплату, название. Вопрос 3 («как часто обновляют одну вакансию») и вопрос 2 («какую зарплату предлагали тогда») требуют истории.

**Вопрос, который я бы задал:** «Нужна ли история *каждого* поля или только значимых? И нужен ли ответ "как было на дату X"?»

## Варианты
1. **SCD тип 1** — перезаписывать строку. Одна таблица, один UPDATE — но история теряется.
2. **Снимок на каждый запуск** — копия всех вакансий при каждой загрузке. Логика загрузки минимальная, но объём растёт на число вакансий × число запусков, и почти все копии повторяют предыдущий снимок (у нас ~44 тыс. строк вместо 1895 версий).
3. **SCD тип 2** — новая версия только при изменении, с периодом действия `[valid_from, valid_to)`.
4. **Журнал событий (event log)** — хранить только изменённые поля.

## Решение
Две таблицы: `vacancy` (тип 1, текущее состояние) + `vacancy_snapshot` (тип 2, история).

## Почему
- Тип 2 хранит ровно столько версий, сколько было изменений.
- Ответ «как было на дату X» — один запрос: `WHERE valid_from <= X AND (valid_to > X OR valid_to IS NULL)`.
- Отдельная таблица текущего состояния избавляет 4 из 6 отчётов от поиска «последней версии».
- Изменение ловим по `content_hash` — SHA-256 от значимых полей. Сравнить две строки по 64 символам проще, чем по 10 колонкам, где часть может быть NULL (а `NULL = NULL` в SQL — это не TRUE).

## Последствия
- (+) История компактная, запросы «на дату» простые.
- (−) Данные дублируются между `vacancy` и текущей версией в `vacancy_snapshot`. Загрузчик обязан менять обе в одной транзакции.
- (−) Навыки в историю не попадают: их изменение создаёт новую версию (они входят в hash), но какие навыки были раньше — не узнать. Осознанное упрощение.
- (−) Мы видим только те изменения, которые попали между двумя нашими запусками. Если вакансию поменяли дважды за сутки, увидим одно изменение.
