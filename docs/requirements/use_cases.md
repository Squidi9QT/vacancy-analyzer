# Use cases (сценарии использования)

**Use case** — описание того, как актор достигает цели с помощью системы: основной поток шагов и что происходит, если что-то пошло не так.

---

## UC-1. Первичная загрузка

| Поле | Значение |
|------|----------|
| Актор | Студент-аналитик |
| Цель | Наполнить пустую базу историей вакансий |
| Предусловия | PostgreSQL запущен, схема создана (`python -m src.main init-db`) |
| Результат | В базе вакансии за период, в `load_run` запись со статусом `success` |

**Основной поток**
1. Студент запускает `python -m src.main backfill --from 2026-03-01 --to 2026-10-30` (на фикстурах) или `load --days 30` (на API).
2. Система создаёт запись в `load_run` со статусом `running`.
3. Для каждой роли (системный аналитик, аналитик данных, junior backend) система запрашивает страницы поиска, пока не дойдёт до последней.
4. Для каждой вакансии система запрашивает детальную карточку (там есть навыки).
5. Система превращает JSON в плоские записи и сохраняет их через `INSERT ... ON CONFLICT`.
6. Если содержимое вакансии изменилось, система закрывает старую версию в `vacancy_snapshot` и добавляет новую.
7. Система обновляет `load_run`: статус `success`, время конца, число записей.

**Альтернативные потоки**
- 3а. API ответил 429 или 5xx → клиент ждёт 1, 2, 4, 8… секунд и повторяет; после 5 неудач — ошибка.
- 3б. API отдаёт не больше 2000 результатов на один поиск. Поэтому система всегда ищет по одному дню публикации: за день вакансий одной роли заметно меньше 2000. Если `found` всё равно больше 2000 — в лог пишется WARNING (данные неполные).
- 5а. Ошибка в данных одной вакансии (нет обязательного поля) → вакансия пропускается, в лог пишется WARNING, загрузка продолжается.
- *а. Любая необработанная ошибка → транзакция текущей вакансии откатывается, `load_run.status = failed`, текст ошибки сохраняется, код возврата 1.

## UC-2. Ежедневное обновление

| Поле | Значение |
|------|----------|
| Актор | Система (cron) |
| Цель | Подтянуть новые и изменённые вакансии за сутки |
| Предусловия | Есть данные первичной загрузки |
| Результат | Новые вакансии добавлены, изменённые — получили новую версию в истории |

**Основной поток**
1. Cron запускает `python -m src.main load --days 1`.
2. Шаги 2–7 из UC-1.
3. Для вакансий, которые уже есть в базе и не изменились, система обновляет только `last_seen_at`.

**Альтернативные потоки**
- 1а. Предыдущий запуск упал → новый запуск идёт как обычно. Благодаря идемпотентности уже записанное не задублируется.
- 1б. Вакансия исчезла из выдачи (закрыта) → в этой версии мы не удаляем её, `last_seen_at` перестаёт обновляться. Решение — в `open_questions.md`, вопрос 6.

## UC-3. Построение отчёта

| Поле | Значение |
|------|----------|
| Актор | Студент-аналитик |
| Цель | Получить ответы на 6 бизнес-вопросов в виде таблиц и графиков |
| Предусловия | В базе есть данные |
| Результат | PNG-графики в `reports/`, данные для сайта в `explainer/data.js` |

**Основной поток**
1. Студент запускает `python -m src.main report`.
2. Система выполняет SQL-запросы из `sql/queries/`.
3. pandas превращает результаты в таблицы, matplotlib рисует графики.
4. Система сохраняет PNG и CSV в `reports/`, а результаты — в `explainer/data.js`.

**Альтернативные потоки**
- 2а. База пустая → отчёт пишет понятное сообщение «нет данных, запустите load», а не падает со стектрейсом.
