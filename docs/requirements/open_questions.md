# Открытые вопросы к заказчику

Аналитик не должен молча додумывать за заказчика. Ниже — вопросы, которые я задал бы до начала разработки. Заказчика у учебного проекта нет, поэтому для каждого вопроса записано **принятое решение** и **почему**. В реальном проекте эти решения нужно согласовать.

---

### 1. Что считать одной вакансией?
**Варианты:** (а) одна вакансия = один `id` на hh.ru; (б) одна вакансия = одинаковые работодатель + название + город; (в) похожий текст описания.
**Решение:** (а) — основной ключ `hh_id`. Вариант (б) используем только как **подсказку** о возможных дублях (запрос q5 показывает их отдельно).
**Почему:** id однозначен и не требует догадок. Работодатель может честно открыть две одинаковые вакансии на двух сотрудников — склеивать их по названию было бы ошибкой. Цена решения: перевыложенная заново вакансия (новый id) посчитается как новая.

### 2. Как обрабатывать вакансии без зарплаты?
**Варианты:** выкинуть из базы; подставить среднее; хранить NULL и исключать из расчёта зарплат.
**Решение:** хранить `NULL`. В расчётах зарплат такие вакансии не участвуют, но участвуют в навыках и в вопросе 4.
**Почему:** отсутствие зарплаты — тоже информация (вопрос 4). Подстановка среднего исказила бы медиану: она стала бы «гуще» в центре.

### 3. Если указана «вилка» от и до — какую цифру брать?
**Решение:** середину вилки. Если указано только «от» — берём «от», только «до» — берём «до».
**Почему:** простое и объяснимое правило. Цена: «от 100 000» реально может значить 100–150 тыс., мы занижаем такие вакансии. Правило записано в одном месте (представление `v_vacancy_salary`), его легко поменять.

### 4. Как сравнивать зарплаты в разных валютах и gross/net?
**Решение:** хранить исходные суммы и валюту как есть. При анализе переводить в рубли по курсу из таблицы `currency` и приводить gross к net умножением на 0,87.
**Почему:** исходные данные не теряются, курс можно обновить и пересчитать. Подробно — ADR-002. Цена: 0,87 — упрощение (с 2025 года НДФЛ прогрессивный: 13–22 %).

### 5. Как хранить историю изменений вакансии?
**Решение:** таблица `vacancy` хранит текущее состояние (перезаписывается), таблица `vacancy_snapshot` — все версии с периодом действия (SCD тип 2). Новая версия появляется, только если изменились значимые поля.
**Почему:** вопрос 3 («как часто обновляют») без истории не ответить. Хранить копию на каждый запуск — лишний объём: 95 % вакансий за день не меняются. Подробно — ADR-003.

### 6. Что делать с закрытыми вакансиями?
**Решение:** не удалять. Поле `last_seen_at` показывает, когда вакансию видели в последний раз.
**Почему:** удаление уничтожит историю для вопросов 2, 3, 6. Цена: в «текущем состоянии» есть уже закрытые вакансии — при анализе активных нужно фильтровать по `last_seen_at`.

### 7. Как определить роль вакансии?
**Варианты:** по поисковому запросу, которым её нашли; по названию вакансии; по профессиональной роли hh.ru.
**Решение:** по правилам на названии (`src/transform/roles.py`); если правило не сработало — по поисковому запросу.
**Почему:** поиск hh.ru ищет и по описанию, поэтому по запросу «системный аналитик» приходят и «бизнес-аналитики», и «тестировщики». Цена: правила нужно поддерживать; их проверяют тесты.

### 8. Какой период и какие города нужны?
**Решение:** все города России + Алматы (для примера с другой валютой); период — с марта 2026.
**Почему:** студенту интересна вся страна, а Томск — отдельно. Хранить весь период дешево: тысячи строк.

### 9. Какой часовой пояс у дат?
**Решение:** все даты храним как `TIMESTAMPTZ` (момент времени с поясом), API отдаёт `+0300`. Месяц для отчётов считаем в московском времени.
**Почему:** вакансия, опубликованная 31-го в 23:30 по Москве, по UTC попала бы в 31-е, а по Томску (+7) — уже в 1-е число следующего месяца. Нужен один договорённый пояс.

### 10. Насколько свежими должны быть данные?
**Решение:** раз в сутки достаточно.
**Почему:** зарплаты и навыки меняются медленно. Чаще — лишняя нагрузка на API.
