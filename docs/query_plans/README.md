# Планы запросов: что было медленным и как это нашли

## Как мерили

**EXPLAIN ANALYZE** выполняет запрос и показывает **план**: по каким шагам (узлам) PostgreSQL его выполнял, сколько строк прошло через каждый узел и сколько это заняло времени. Узлы читаются изнутри наружу: самый вложенный выполняется первым.

На рабочей базе (1162 вакансии) все запросы выполняются за 1–15 мс. На маленьких таблицах PostgreSQL почти всегда выбирает полное чтение таблицы (Seq Scan), потому что так дешевле, чем ходить по индексу. Поэтому на таких данных мерить бесполезно.

Для замеров сделана отдельная база `vacancies_bench`: 300 000 вакансий, 600 846 версий, 1,49 млн связей «вакансия-навык» (`scripts/bench_scale.sql`). Планы сохраняет `scripts/explain.sh`.

```bash
createdb vacancies_bench
psql -d vacancies_bench -f sql/001_schema.sql
psql -d vacancies_bench -f scripts/bench_scale.sql
scripts/explain.sh vacancies_bench sql/queries/q5_new_last_7_days.sql docs/query_plans/q5_before.txt
```

## q6: проблема в запросе, а не в индексах

Файлы: [`q6_before.txt`](q6_before.txt), [`q6_after.txt`](q6_after.txt).

**Что увидели в плане «до»:**

```
SubPlan 2
  ->  Aggregate  (actual time=0.769..0.769 rows=1 loops=5009)
        ->  CTE Scan on active_months am  (actual time=0.086..0.769 rows=8 loops=5009)
              Filter: (employer_id = numbered.employer_id)
              Rows Removed by Filter: 39958
```

- `loops=5009` — подзапрос выполнен 5009 раз, по разу на каждую строку результата.
- `Rows Removed by Filter: 39958` — каждый раз он читал весь CTE (40 тыс. строк), чтобы найти 8 нужных.
- 5009 × 0,77 мс ≈ 3,9 с из 4,0 с всего запроса.

**Почему индекс не поможет:** CTE — временный результат в памяти, индексов у него нет и создать их нельзя.

**Что сделали:** число активных месяцев компании теперь считает оконная функция `count(*) OVER (PARTITION BY employer_id)` в том же проходе, где `ROW_NUMBER`. Результат тот же, проверено на рабочей базе.

**Урок:** «медленно» не всегда значит «нужен индекс». Сначала смотрим план и ищем узел, где ушло время (большое `loops` × время одного прохода).

## q5: нужны индексы

Файлы: [`q5_before.txt`](q5_before.txt), [`q5_after.txt`](q5_after.txt).

**Что увидели в плане «до»:**

1. `Seq Scan on vacancy v ... rows=300000` и `Rows Removed by Join Filter: 291261` — чтобы найти 8 739 новых вакансий (3 %), прочитали все 300 тыс.
2. `SubPlan 1 ... loops=8589` с `BitmapAnd` двух индексов (`employer_id` и `area_id`) — поиск дубля для каждой новой вакансии. 8589 × 0,136 мс ≈ 1,17 с. **Основное время ушло сюда.**

**Что сделали** (`sql/002_indexes.sql`):

```sql
CREATE INDEX idx_vacancy_first_seen_at ON vacancy (first_seen_at);
CREATE INDEX idx_vacancy_duplicate_lookup ON vacancy (employer_id, area_id, lower(name), created_at);
```

**Что стало в плане «после»:**
- `Bitmap Index Scan on idx_vacancy_first_seen_at` — читаем только свежие вакансии.
- `Index Scan using idx_vacancy_duplicate_lookup ... actual time=0.001` — поиск дубля одним спуском по дереву вместо склейки двух индексов.

**Почему порядок колонок в составном индексе именно такой:** B-tree упорядочен по первой колонке, внутри неё — по второй, и так далее. Колонки с условием «равно» ставим первыми, колонку с диапазоном (`created_at >= ... AND created_at < ...`) — последней. Тогда нужные строки лежат в индексе одним непрерывным куском.

**Почему `lower(name)`, а не `name`:** в запросе стоит `lower(d.name) = lower(v.name)`. Индекс по `name` для такого условия не используется: база не знает, что `lower()` сохраняет порядок. Нужен индекс по выражению.

**Что осталось:** `Seq Scan on vacancy_snapshot prior` (~28 мс). Планировщик оценил новых вакансий в 100 000 (`rows=100000`), а их 8 739. Причина: граница окна вычисляется в CTE `params`, и на этапе планирования значение неизвестно. Тогда PostgreSQL берёт стандартную оценку «треть строк» и выбирает хеш-соединение по всей таблице версий. Если подставить дату константой, оценка станет точной. Мы оставили CTE: запрос должен работать без параметров. Цена — ~28 мс.

**Цена индексов:** каждая вставка или обновление вакансии теперь обновляет ещё 2 индекса. Для загрузки сотен вакансий в день это незаметно. Для массовой заливки миллионов строк индексы иногда удаляют и создают заново после неё.

## q2: тяжёлый, но оправданно

Файл: [`q2_plan.txt`](q2_plan.txt).

Что интересного в плане:
- `Index Scan using uq_snapshot_vacancy_valid_from` — для `ROW_NUMBER() OVER (PARTITION BY vacancy_id ORDER BY valid_from)` сортировка не нужна. Уникальный индекс `(vacancy_id, valid_from)` уже отдаёт строки в нужном порядке. Этот индекс появился «бесплатно» вместе с ограничением `UNIQUE`.
- `Run Condition: (row_number() OVER (?) <= 1)` — оптимизация PostgreSQL 15+: функция перестаёт нумеровать строки вакансии после первой, раз нужна только `version_no = 1`.
- `Sort Method: external merge Disk: 6928kB` — сортировка не поместилась в `work_mem` (4 МБ) и ушла на диск. **Мы проверили гипотезу:** с `SET work_mem = '32MB'` сортировка идёт в памяти, но время то же (627 мс). Узкое место не здесь.
- Основное время — вложенные циклы по 300 тыс. строк (`Nested Loop ... loops=194892`). Планировщик ошибся в 100 раз (`rows=3004` вместо 300 000): он не умеет оценивать фильтр `version_no = 1` по результату оконной функции.

**Почему оставили:** запрос по смыслу читает всю историю, 0,6 с для отчёта раз в день приемлемо. Если нужно быстрее — **материализованное представление** с помесячными агрегатами, которое обновляется после загрузки (`REFRESH MATERIALIZED VIEW`). Цена: данные в отчёте отстают до следующего обновления.
